# ADR-006: Testing strategy

Status: Accepted
Date: 2026-08-16

## Context

Correctness in this service is dominated by the data-cleansing pipeline,
where a subtly wrong rule silently corrupts or drops real data rather than
crashing loudly. That risk profile needs more than "does the endpoint
return 200". It needs exact behavior pinned for individual dirty values,
end-to-end behavior verified against the actual challenge files rather than
synthetic fixtures, and proof that the container really runs the way the
Dockerfile claims.

## Options Considered

- **Layered pyramid: unit + integration + e2e-real-data + container smoke
  (chosen)** — Pure-function unit tests exercise each normalization rule
  (N1–N7) and quarantine rule (Q1–Q5) with table-driven cases built from
  the literal dirty values found in profiling: `" STORE_A "`, `"1001.0"`,
  `23/01/2024`, `-5`. Integration tests exercise the FastAPI app against a
  temporary SQLite database with small handcrafted dirty fixture CSVs,
  asserting exact report numbers and endpoint semantics (404/422/empty-list,
  idempotent re-ingest). End-to-end tests ingest the actual four challenge
  CSVs and assert exact counts pinned in `tests/e2e/expected_counts.json`,
  itself generated by an independent profiling script, so the "expected"
  numbers are derived twice rather than copied from the implementation.
  Container smoke tests build the image, run it, and curl it. The layering
  gives fast, precise failures for rule bugs while still proving the whole
  system works against real data and a real container. It is also the most
  test code to write and maintain of the three options.
- **Real-data-only testing** — Skip handcrafted fixtures and unit tests;
  test everything against the four actual CSV files. This catches
  real-world regressions but localizes failures poorly (a failing assertion
  on "24,398 rows loaded" doesn't say *which* rule regressed) and cannot
  exercise edge cases absent from the real files, such as a malformed date
  format that doesn't happen to occur in this dataset but could in a future
  upload.
- **Property-based testing only** (Hypothesis generating arbitrary strings
  for the normalization functions) — Excellent at finding edge cases nobody
  would write by hand, but on its own it doesn't verify measured behavior
  against the real, messy files. A generated random string is a different
  kind of input from "the literal values profiling found in
  `order_recommendations.csv`." A complement to example-based tests, not a
  replacement.

## Decision

Use the **four-layer pyramid**: unit tests (`tests/unit/`, one rule ↔ one
test module, no DB), integration tests (`tests/integration/`, FastAPI
`TestClient` + temp SQLite + handcrafted fixture CSVs per defect class),
end-to-end tests (`tests/e2e/`, real challenge CSVs, counts pinned against
an independently generated `expected_counts.json`), and container smoke
tests (build → run → curl `/health` → ingest → query, marked `-m smoke` so
it can be skipped where Docker is unavailable). A coverage gate of ≥90%
line+branch on `app/` is enforced via `pytest-cov`.

## Consequences

Rule regressions fail at the unit level with a precise, single-rule
message instead of surfacing three layers up as an aggregate count
mismatch. Deriving the e2e counts from an independent profiling script,
rather than reading them off the first successful run of the
implementation, guards against the classic failure mode where the test
simply encodes whatever the code currently does. And because the smoke test
carries its own marker, the rest of the suite runs anywhere, with or
without Docker, while CI still runs the full pyramid.

Two costs worth stating:

- Four distinct layers is more code and more suite runtime than a
  single-layer approach, and keeping them from drifting apart (a fixture
  CSV that no longer represents the defect class it claims) is ongoing
  maintenance.
- Pinned e2e counts cut both ways. Any legitimate change to a rule's
  behavior means deliberately regenerating and re-reviewing
  `expected_counts.json`. That friction is the point, but it does give a
  trivial rule tweak a wider blast radius than looser assertions would.
