# ADR-006: Testing strategy

Status: Accepted
Date: 2026-08-16

## Context

Correctness in this service is dominated by the data-cleansing pipeline,
where a subtly wrong rule silently corrupts or drops real data rather than
crashing loudly. That risk profile calls for a test strategy that goes
beyond "does the endpoint return 200": it needs to pin exact behavior for
individual dirty values, verify end-to-end behavior against the actual
challenge files (not just synthetic fixtures), and verify the container
actually runs the way the Dockerfile claims it does.

## Options Considered

- **Layered pyramid: unit + integration + e2e-real-data + container smoke
  (chosen)** — Pure-function unit tests exercise each normalization rule
  (N1–N7) and quarantine rule (Q1–Q5) with table-driven cases built from the
  literal dirty values found in profiling (`" STORE_A "`, `"1001.0"`,
  `23/01/2024`, `-5`). Integration tests exercise the FastAPI app against a
  temporary SQLite database with small handcrafted dirty fixture CSVs,
  asserting exact report numbers and endpoint semantics (404/422/empty-list,
  idempotent re-ingest). End-to-end tests ingest the actual four challenge
  CSVs and assert exact counts pinned in `tests/e2e/expected_counts.json`
  (itself generated by an independent profiling script, so the "expected"
  numbers are derived twice rather than copied from the implementation).
  Container smoke tests build the image, run it, and curl it. This layering
  gives fast, precise unit-level failures for rule bugs while still proving
  the whole system works against real data and a real container — but it is
  the most test code to write and maintain of the three options.
- **Real-data-only testing** — Skip handcrafted fixtures and unit tests;
  test everything against the four actual CSV files. This would catch
  real-world regressions but gives poor failure localization (a failing
  assertion on "24,398 rows loaded" doesn't say *which* rule regressed) and
  cannot exercise edge cases that may not be well-represented in the real
  files (e.g. a specific malformed date format that happens not to occur
  in this particular dataset but could occur in a future upload).
- **Property-based testing only** (e.g. Hypothesis generating arbitrary
  strings for normalization functions) — Excellent at finding edge cases a
  human wouldn't think to write by hand, but on its own it doesn't verify
  the actual measured behavior against the real, messy files this service
  must handle — a generated random string is a different kind of test
  input than "the literal values profiling found in `order_recommendations.csv`."
  It is a valuable complement to, not a replacement for, example-based unit
  tests pinned to real dirty values.

## Decision

Use the **four-layer pyramid**: unit tests (`tests/unit/`, one rule ↔ one
test module, no DB), integration tests (`tests/integration/`, FastAPI
`TestClient` + temp SQLite + handcrafted fixture CSVs per defect class),
end-to-end tests (`tests/e2e/`, real challenge CSVs, counts pinned against
an independently generated `expected_counts.json`), and container smoke
tests (build → run → curl `/health` → ingest → query, marked `-m smoke` so
it can be skipped where Docker is unavailable). A coverage gate of ≥90%
line+branch on `app/` is enforced via `pytest-cov`.

## Consequences

**Positive:**

- Rule regressions fail at the unit level with a precise, single-rule
  message, rather than only surfacing as an aggregate count mismatch three
  layers up.
- The e2e counts being derived by an independent profiling script (rather
  than by reading them off a first successful run of the implementation)
  guards against the common failure mode of "the test just encodes
  whatever the code currently does."
- The smoke test's own marker means the rest of the suite is fully
  runnable in environments without Docker (e.g. a quick local `pytest -m
  "not smoke"`), while CI still runs the full pyramid.

**Negative:**

- Four distinct test layers is meaningfully more code and more test-suite
  runtime than a single-layer approach; keeping them from drifting apart
  (e.g. a fixture CSV that no longer represents a defect class it claims
  to) is an ongoing maintenance cost.
- Pinned e2e counts are a double-edged sword: any legitimate change to a
  rule's behavior requires deliberately regenerating and re-reviewing
  `expected_counts.json`, which is friction by design but does mean a
  trivial rule tweak has a wider blast radius on the test suite than it
  would with looser assertions.
