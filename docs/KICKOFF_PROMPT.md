# FreshFlow — Agent Team Kickoff Prompt

> Paste this prompt (together with `PLAN.md` and the `engineering-challenge/` folder) into the orchestrating agent to launch the fully autonomous build. ## PROMPT

You are **A0, the orchestrator** of an autonomous engineering team. Build the complete FreshFlow challenge solution exactly as specified in the attached `PLAN.md`. Do not ask a human anything; every decision you need is already made in the plan. If you hit a genuinely unspecified detail, choose the option most consistent with the plan's principles (normalize what is unambiguous, quarantine what is not, report everything) and capture it as a new numbered ADR in `docs/adr/` (MADR format: context → options with pros/cons → decision → consequences). **Every architectural or technology decision — up-front or made in flight — must exist as an ADR.** ADR-001–012 are pre-specified in PLAN.md §2/§2.1; the numbering continues from there.

### Mission

A containerized FastAPI + SQLite service (Python 3.12, SQLAlchemy 2.0, Pydantic v2, uv, ruff, pytest) that:

1. `POST /api/v1/ingest/{dataset}` — ingests the four challenge CSVs (`items`, `inventory`, `orderable-items`, `order-recommendations`) via multipart upload with **normalize + quarantine + full JSON ingest report** semantics (rules N1–N7, Q1–Q5 in PLAN.md §4), replace-per-dataset, atomic.
2. `GET /api/v1/stores/{store_id}/recommendations?day=YYYY-MM-DD` — enriched recommendations (catalog join, same-day inventory, orderable window, tags), store_id normalization on input.
3. Supporting endpoints: past ingest reports, quarantine audit listing, store listing, `/health`, auto OpenAPI.
4. Repository layout, data model, API contract: follow PLAN.md §3–§5 **exactly** — these are frozen contracts.

Deliverables: working repo at `freshflow-service/` with green tests (unit + integration + e2e real data + container smoke, ≥90% coverage, `ruff check` clean, `mypy --strict` clean on `app/`), Dockerfile (multi-stage, non-root, HEALTHCHECK), CI workflow, and complete documentation (README, ARCHITECTURE.md with Mermaid diagrams, the full ADR set 001–012+ with alternatives/pros/cons, DATA_QUALITY.md). Git history: conventional commits, one coherent commit per phase/lane.

### Code quality standard (CI-blocking, applies to every agent)

Latest Python best practices, readable and well-documented code — enforced per PLAN.md §2.2: Python 3.12 idioms, full type annotations everywhere (`mypy --strict` must pass), `pathlib`, `StrEnum` for reason codes/dataset kinds, Pydantic models over dict-passing, thin routers / pure rule functions / orchestrating services, structured `logging` (never `print`), Google-style docstrings on every public module/class/function, and rule functions citing their rule IDs (N1–N7, Q1–Q5) in docstrings. `ruff check` (incl. pydocstyle for public APIs, bugbear) is a merge gate identical in weight to tests.

### Verification of every rule (PLAN.md §6.1 — implement it, don't summarize it)

Every standard has a named, automated check; build them as part of the work, not after:

- **ruff**: `select = ["E","W","F","I","N","B","UP","SIM","C4","RUF","D"]`, Google docstring convention, py312 target, `D` relaxed in `tests/`; plus `ruff format --check`.
- **mypy**: `strict = true` on `app/`.
- **pytest**: unit tests named 1:1 after rules (`test_n1_…`…`test_q5_…`); a **traceability meta-test** asserting every rule ID N1–N7/Q1–Q5 appears in exactly one implementing function docstring and one test module; integration tests per endpoint; **OpenAPI snapshot test** (committed `openapi.json`, drift = failure); coverage `--cov=app --cov-branch --cov-fail-under=90`.
- **e2e**: expected counts in `tests/e2e/expected_counts.json`, generated by a committed standalone profiling script — counts derived independently from the service code.
- **docker**: `hadolint` on the Dockerfile; smoke test that builds, runs, curls health → ingests all four files → queries, and asserts non-root `USER` + `HEALTHCHECK` via `docker inspect`.
- **docs meta-test**: every ADR file contains Context / Options (with pros/cons) / Decision / Consequences sections.
- **CI** (`.github/workflows/ci.yml`), fail-fast: `lint` → `typecheck` → `test` → `e2e` → `docker`. Identical commands runnable locally via `uv run`; agents run them **before** committing — CI confirms, it doesn't discover.

### Ground truth about the data (verified — do not re-litigate)

- `store_id` appears in 8 variants (case + surrounding whitespace) → N1 normalize.
- `order_recommendations.csv` has float item numbers (`"1001.0"`) → N2; **515 negative quantities** → Q1 quarantine; items `1099, 9901, 9902, 9903` missing from catalog → Q2.
- `inventory.csv` has **803 `DD/MM/YYYY` dates** (day-first proven by `23/01/2024`) → N3; **~22.4k fractional quantities** → store exact, warn, expose rounded `current_inventory` (N6).
- All duplicate keys (inv 120, rec 295, orderable 195) carry identical payloads → N7 dedupe-and-count.
- ~3.6k recommendations lack an orderable window → load + warn (not quarantine).
- Categories/tags have casing+whitespace noise → N4/N5.

Your e2e suite must pin exact counts: generate `tests/e2e/expected_counts.json` with a standalone profiling script (committed) run against `data/`, then assert ingest reports match it.

### Team & execution graph

Spawn subagents per lane; run Phase 2 lanes **in parallel**. Each lane owns an exclusive file set (PLAN.md §7.1) and must not touch files outside it — you enforce this at merge.

**Phase 1 — you + A1 Platform (serial, keep it short):**
A1 scaffolds the full repo skeleton: pyproject (uv), ruff+pytest config, `app/config.py`, `app/db.py`, all ORM models per §4.1, Dockerfile, `.github/workflows/ci.yml`, `/health`. You then commit the **frozen contracts**: Pydantic schemas in `app/schemas/`, stub files for `app/ingest/{parser,normalize,rules,service,router}.py` and `app/recommendations/`, `app/stores/` with exact signatures + docstrings + `NotImplementedError`. Nothing in Phase 2 may alter a signature; a lane needing a change must route it through you.

**Phase 2 — four parallel lanes:**

- **A2 Data engineer** — implement `parser.py`, `normalize.py` (N1–N7 as pure functions), `rules.py` (Q1–Q5, reason-code enum) + exhaustive table-driven unit tests in `tests/unit/` covering every literal dirty value listed above. Skills: data wrangling, Pydantic, edge-case testing.
- **A3 Backend/ingest** — `ingest/service.py` (stream → normalize → validate → transactional replace-load → report build → persist `ingest_jobs` + `quarantine_rows`), `ingest/router.py`, upload size limit, header validation with 400 report; integration tests with handcrafted dirty fixture CSVs in `tests/fixtures/`, asserting exact report JSON. Skills: FastAPI, transactions, streaming IO.
- **A4 Backend/query** — recommendations + stores routers/services: enrichment joins (catalog, same-day inventory, orderable window with price override + tags), store_id-insensitive lookup, 404/422/empty-list semantics; integration tests. Skills: FastAPI, SQL query design.
- **A6 Tech writer** — `docs/adr/ADR-001…012.md` (content from PLAN.md §2 + §2.1, expanded with full MADR context/options/consequences), `docs/ARCHITECTURE.md` with Mermaid: C4 container diagram, component diagram, ERD, ingest sequence diagram, request-flow diagram; `docs/DATA_QUALITY.md` mapping every measured defect → rule → count. Leave README numbers as placeholders. Skills: technical writing, Mermaid/C4.

**Phase 3 — integration + verification:**
You merge lanes, resolve nothing by rewrite (contracts made conflicts impossible — if one appears, the violating lane redoes it). Then **A5 QA**: e2e real-data suite with pinned counts, spot-check assertions (e.g. store_a/2024-01-01/item 1001 → qty 18, delivery 2024-01-02; a `" STORE_A "`-variant query resolves), container smoke test (`docker build`, `docker run`, curl health→ingest all four→query), `scripts/load_all.sh`, coverage gate ≥90%. Skills: pytest, Docker, adversarial testing.

**Phase 4 — review + docs finalization (parallel):**
**A7 Reviewer** re-derives the acceptance checklist from PLAN.md §8 and adversarially reviews: spec compliance per endpoint, error paths, atomicity of replace-ingest, upload limits, injection surface, container hardening (non-root, slim, healthcheck), test honesty (do e2e counts really come from the data?). Every finding: CONFIRMED with repro, or dropped. A6 finalizes README (quickstart verified by literally executing it, real report numbers, API examples with curl).

**Phase 5 — you:** fix all CONFIRMED findings, rerun the entire gate (quality gates in PLAN.md §7.4, all six), produce final clean git history, report completion with: gate results table, final ingest report JSON for all four files, and tree of the repo.

### Model assignment (PLAN.md §7.3 — apply when spawning each agent)

Match model tier to the judgment content of the lane, not its code volume: **A2 Data engineer → Opus, high effort** (defect-sensitive rule logic — the heart of the challenge); **A7 Reviewer → Fable, high effort** (adversarial verification is the hardest task; the strongest model goes where verification happens); **A5 QA → Sonnet, high effort**; **A1, A3, A4, A6 → Sonnet, medium effort** (well-specified work against frozen contracts). You (A0) run on the session model (Fable). No Haiku anywhere — every lane owns correctness-critical output.

### Hard rules

- Tests are written **in the same phase** as the code they test, by the owning agent — never deferred.
- Any non-trivial decision an agent makes in flight ships as a micro-ADR in the same commit — a decision without an ADR is a gate failure.
- No agent edits files outside its ownership set.
- Never mark the mission complete while any gate fails. If Docker is unavailable in the environment, run the smoke test via the `-m smoke` marker path and report it as environment-blocked — everything else must still be green.
- All numbers in docs must be produced by running code, never estimated.
